# Terraform — AWS infrastructure

This folder contains **Infrastructure as Code** for the Document Search project. There are two separate Terraform setups:

| Path | Purpose | When to use |
|------|---------|-------------|
| **`/`** (root) | Full stack: VPC, EC2, S3 bucket, Lambda, etc. | Production-style deploy (Phase 6); creates **new** resources |
| **`lambda-deploy/`** | Lambda + IAM role + log group only | **Phase 4.3** — attach to your **existing** bucket |

Most local/dev work uses **`lambda-deploy/`** with bucket **`ai-pdss`** in **`il-central-1`**.

---

## What we set up (Phase 4 — AWS)

### 4.1 — S3 & IAM (console)

- **S3 bucket:** `ai-pdss` (Israel / `il-central-1`)
- **Prefix:** `documents/` (matches NestJS upload keys)
- **Security:** Block public access ON, SSE-S3 encryption, no CORS (uploads go through the API)
- **IAM user:** `yaroslav@Dev` with programmatic access
- **Inline policy:** `ocumentSearchS3Access` — `ListBucket`, `GetObject`, `PutObject`, `DeleteObject` on `ai-pdss`

### 4.2 — Backend credentials

NestJS reads AWS from `backend/.env`:

```env
AWS_REGION=il-central-1
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_S3_BUCKET=ai-pdss
```

Terraform and the AWS CLI **do not** read `backend/.env`. Use the same keys via:

```powershell
aws configure
# or
$env:AWS_ACCESS_KEY_ID = "..."
$env:AWS_SECRET_ACCESS_KEY = "..."
$env:AWS_DEFAULT_REGION = "il-central-1"
```

### 4.3 — Lambda (this repo + `lambda-deploy/`)

| Piece | Name / location |
|-------|------------------|
| Lambda function | `ai-pdss-document-processor` |
| Runtime | Node.js 20.x |
| Handler | `index.handler` |
| Source code | `lambda-function/index.js` |
| Deploy package | `lambda-deploy/lambda_function.zip` (built, not committed) |
| Execution role | `ai-pdss-document-processor-role` (S3 read on `ai-pdss`) |
| Log group | `/aws/lambda/ai-pdss-document-processor` |
| S3 trigger | **Off** by default (`enable_s3_trigger = false`) |

**Behavior:** On invoke (or S3 event if enabled), Lambda downloads a file under `documents/`, extracts text (`.txt`, `.pdf`, `.docx`), and logs the result. Full indexing (Postgres, Elasticsearch, AI) still runs in the **NestJS Bull** processor.

**IAM for Terraform deploy:** Customer managed policy `DocumentSearchTerraformLambdaDeploy` — see `lambda-deploy/iam-terraform-deploy-policy.json`.

## Quick start — Lambda deploy (`lambda-deploy/`)

### Prerequisites

- [Terraform](https://www.terraform.io/downloads) >= 1.0
- [AWS CLI](https://aws.amazon.com/cli/) configured
- Node.js 18+
- S3 bucket `ai-pdss` already exists
- IAM user with:
  - S3 policy on `ai-pdss` (app uploads)
  - `DocumentSearchTerraformLambdaDeploy` (Terraform apply) — attach from `lambda-deploy/iam-terraform-deploy-policy.json`

### 1. Build the deployment zip

```powershell
cd terraform/lambda-function
npm run build
```

Output: `terraform/lambda-deploy/lambda_function.zip` (~13 MB).

### 2. Configure variables

```powershell
cd ..\lambda-deploy
copy terraform.tfvars.example terraform.tfvars
```

Defaults match this project (`ai-pdss`, `il-central-1`). Edit only if your names differ.

**Do not commit** `terraform.tfvars` (may contain account-specific choices; secrets belong in `.env`, not Terraform).

### 3. Deploy

```powershell
terraform init
terraform plan
terraform apply
```

Type `yes` when prompted.

### 4. Test invoke

```powershell
aws lambda invoke `
  --function-name ai-pdss-document-processor `
  --region il-central-1 `
  --payload file://../lambda-function/test-event.json `
  --cli-binary-format raw-in-base64-out `
  response.json

Get-Content response.json
```

Update `lambda-function/test-event.json` if the S3 object key changed.

### 5. View logs

```powershell
aws logs tail /aws/lambda/ai-pdss-document-processor --region il-central-1 --since 10m --follow
```

### Show outputs

```powershell
cd terraform/lambda-deploy
terraform output
```

### Enable S3 trigger (optional)

Edit `lambda-deploy/terraform.tfvars`:

```hcl
enable_s3_trigger = true
```

Then `terraform apply`. **Warning:** Every new object under `documents/` will invoke Lambda **and** the app may still process via Bull. Use one path in production.

You may need extra IAM on your user for `s3:PutBucketNotification` / `s3:GetBucketNotification` on `ai-pdss`.

### Destroy Lambda stack only

```powershell
cd terraform/lambda-deploy
terraform destroy
```

Does **not** delete bucket `ai-pdss` or objects inside it.

### Untaint resources (after failed apply)

If apply failed mid-way and resources are **tainted**:

```powershell
terraform untaint aws_lambda_function.document_processor
terraform untaint aws_cloudwatch_log_group.lambda
terraform apply
```

Or let Terraform replace them (destroy + create) on the next successful apply.

### Full stack (root `terraform/`)

For VPC + EC2 + new S3 bucket (different from `ai-pdss` dev setup):

```powershell
cd terraform
copy terraform.tfvars.example terraform.tfvars
# Create state bucket first (see DEPLOYMENT.md)
terraform init
terraform plan
terraform apply
```

Uses backend bucket `document-search-terraform-state` in `main.tf` — set up separately before first run.

## Troubleshooting

| Error | Fix |
|-------|-----|
| `InvalidClientTokenId` | Run `aws configure` with same keys as `backend/.env`, or create a new access key in IAM |
| `AccessDenied` on `lambda:*` / `logs:*` | Update `DocumentSearchTerraformLambdaDeploy` from `iam-terraform-deploy-policy.json` |
| `logs:DescribeLogGroups` denied | Policy needs `DescribeLogGroups` with `"Resource": "*"` |
| `logs:ListTagsForResource` denied | Add tag actions from latest `iam-terraform-deploy-policy.json` |
| Plan wants to **replace** tainted Lambda/logs | Normal after partial failure; `apply` with `yes` or `terraform untaint` |
| Invoke returns 404 / empty text | Fix `test-event.json` key — object must exist in `ai-pdss` |
| `lambda:InvokeFunction` denied on invoke | Add `lambda:InvokeFunction` to `DocumentSearchTerraformLambdaDeploy` (see `iam-terraform-deploy-policy.json`) |

## What is Terraform?

**Terraform** is an **Infrastructure as Code (IaC)** tool by HashiCorp. Instead of clicking through the AWS Console to create a Lambda function, IAM role, and log group one by one, you describe those resources in **configuration files** (`.tf`), and Terraform creates or updates them for you.

### Why use it?

| Manual console | Terraform |
|----------------|-----------|
| Hard to repeat exactly | Same config → same result every time |
| No history of what changed | Files in Git show what infrastructure should look like |
| Easy to forget a step | One `apply` creates everything in the plan |
| “Works on my machine” | Team shares `main.tf` + `terraform.tfvars` |

For this project, Terraform deployed **`ai-pdss-document-processor`**, its **IAM role**, and the **CloudWatch log group** in one go.

### Core ideas

**1. Resources** — Things in AWS (or other clouds), defined in `.tf` files:

```hcl
resource "aws_lambda_function" "document_processor" {
  function_name = "ai-pdss-document-processor"
  runtime       = "nodejs20.x"
  # ...
}
```

**2. Provider** — Plugin that talks to AWS (uses your credentials):

```hcl
provider "aws" {
  region = "il-central-1"
}
```

**3. State** — A file (`terraform.tfstate`) that records what Terraform already created, so the next run knows what to create, update, or delete. **Keep it local** for learning; teams often store it remotely (S3 backend in root `main.tf`).

**4. Variables** — Inputs (`variables.tf` + `terraform.tfvars`) so you can change bucket name or region without editing every file.

**5. Outputs** — Values printed after apply (e.g. Lambda ARN), defined in `outputs.tf`.

**6. Plan vs apply**

- **`terraform plan`** — “Here’s what I *would* do” (dry run). Safe to run anytime.
- **`terraform apply`** — Actually calls AWS APIs. You confirm with `yes`.

## How to use Terraform (workflow)

### One-time setup

1. Install Terraform: https://developer.hashicorp.com/terraform/install  
2. Configure AWS credentials (`aws configure` or env vars).  
3. `cd` into the folder you want (e.g. `terraform/lambda-deploy`).

### Every time you deploy or change infrastructure

```text
┌─────────────────┐
│  Edit .tf files │  (or terraform.tfvars)
└────────┬────────┘
         ▼
┌─────────────────┐
│ terraform init  │  First time in folder, or after adding providers
└────────┬────────┘
         ▼
┌─────────────────┐
│ terraform plan  │  Review changes (+ / ~ / -)
└────────┬────────┘
         ▼
┌─────────────────┐
│ terraform apply │  Type yes → AWS resources updated
└────────┬────────┘
         ▼
┌─────────────────┐
│ terraform output│  Optional: show ARNs, names
└─────────────────┘
```

### Symbols in `plan` output

| Symbol | Meaning |
|--------|---------|
| `+` | **Create** new resource |
| `~` | **Update** in place |
| `-` | **Destroy** resource |
| `-/+` | **Replace** (destroy then create) |

### Common commands

| Command | What it does |
|---------|----------------|
| `terraform init` | Download AWS provider, prepare backend |
| `terraform fmt` | Format `.tf` files nicely |
| `terraform validate` | Check syntax (no AWS calls) |
| `terraform plan` | Preview changes |
| `terraform apply` | Apply changes |
| `terraform destroy` | Remove all resources in this folder’s state |
| `terraform output` | Print output values |
| `terraform state list` | List resources Terraform manages |

### How this maps to our Lambda deploy

| You do | Terraform does |
|--------|----------------|
| `npm run build` in `lambda-function/` | Builds `lambda_function.zip` (not Terraform — just the code package) |
| `terraform apply` in `lambda-deploy/` | Creates/updates Lambda, IAM role, policies, log group |
| `aws lambda invoke ...` | Tests the function (AWS CLI, not Terraform) |

Terraform **does not** run your Lambda code; it only **provisions** the function and wires permissions. Running the handler is `aws lambda invoke` or an S3 trigger.

### Credentials reminder

Terraform uses the **same AWS identity** as the CLI (`aws sts get-caller-identity`). It does **not** read `backend/.env`. Your IAM user needs permissions for every API call in the plan (hence `DocumentSearchTerraformLambdaDeploy`).

### When something goes wrong

1. Read the **error line** — usually missing IAM action or bad credentials.  
2. Fix IAM or credentials, wait ~30 seconds.  
3. Run `terraform apply` again (often no destroy needed).  
4. If resources are **tainted** after a failed apply, either apply again (replace) or `terraform untaint <resource>`.
